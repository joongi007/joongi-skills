# 클라이언트의 도구 검색·캐시를 포함한 재측정

조사일: 2026-11-11. 이전의 tools/list JSON 크기만으로 모델 컨텍스트·성능을 판단한 해석을
대체한다. 원래 수치는 전송 목록 크기와 프로세스 측정으로만 유효하다.

## 결론

MCP 서버가 도구를 제공하는 것, 클라이언트가 도구를 검색하는 것, 모델이 전체 스키마를 읽는
것은 서로 다른 단계다. 허브가 모든 native 도구를 제공해도 클라이언트가 지연 로딩할 수 있다.
따라서 등록·연결 수나 tools/list 크기만으로 성능을 나쁘다고 판정하지 않는다.

검색은 추가 탐색 단계와 도구 결과를 발생시킨다. 총 입력을 줄여도 캐시 읽기 비율이 바뀌면
비캐시 입력이나 전체 시간이 반드시 줄지는 않는다. 현재 Hub를 검색 전용으로 강제 변경하거나
Apps metadata를 숨기는 결정을 이 작은 실험으로 내리지 않는다.

## 실험을 분리한 이유

1. **실제 모델 실행:** 설치된 Codex CLI와 현재 계정의 모델을 사용해 실제 usage와 과제 결과를 기록했다.
2. **요청 구조 캡처:** 설치된 Claude Code를 loopback 모형 API에 연결해 검색 전후 요청을 확인했다.
   모형이 도구를 선택하도록 응답을 정했으므로 이는 모델의 검색 정확도 실험이 아니다.
3. **기존 리소스 측정:** 프로세스 RSS·도구 목록 바이트는 이전 자료를 유지하지만 실제 토큰과 구분했다.

Claude의 로컬 auth status는 로그인되지 않은 상태로 보고돼, 실제 Claude 모델 성능은 측정하지
않았다. 모형 API가 반환한 가짜 usage·cost는 모든 성능 집계에서 제외했다.

## 실제 Codex 실행 조건

- Codex CLI 0.167.0, 기존 설정과 같은 `gpt-6.1-sol`, reasoning effort `high`.
- 실제 Hub와 stdio backend를 사용하되 사용자 자료가 없는 합성 읽기 전용 도구를 제공했다.
- 도구 수 10개 또는 100개. 관련 도구는 상품 가격과 세율 조회 2개로 동일하고 나머지는 다른 분야다.
- 사용자 config·rules와 host skill discovery는 제외한 격리 실행이다. 개인 공용 설정을 바꾸지 않았다.
- 모든 조건에서 MCP 준비 완료를 요구하고 두 Hub 도구만 합성 과제용으로 사전 승인했다.
  generic hub_call을 실제 제품에서 읽기 전용으로 표시하거나 전역 자동 승인한 것은 아니다.
- 무도구 응답과 가격·세율 조회 과제를 4조건 × 2과제 × 2회, 총 16회 수행했다.
- 2번째 반복은 조건 순서를 뒤집었다. 캐시를 임의로 비우지 않고 실제 cached_input_tokens를 기록했다.
- 합성 조회는 SKU AX-7 가격 13,700원, KR 세율 0.1, 수량 3의 소계 41,100원·총액 45,210원을
  요구했다. 답뿐 아니라 backend에서 실제 두 조회가 호출됐는지도 검증했다.

| 조건 | 의미 |
|---|---|
| 기본 native 10 | 연결된 분석 도구 10개와 Hub 기본 도구를 클라이언트에 제공 |
| 기본 native 100 | 연결된 분석 도구 100개와 Hub 기본 도구를 제공 |
| direct 생략 설정 100 | 같은 목록에 Codex의 omit_tools_from=[direct] 설정 적용 |
| Hub 검색 경로 100 | 실험용 어댑터가 hub_search·hub_call만 노출, backend 도구는 검색 결과로 사용 |

`direct 생략` 조건에서 관측된 실제 경로도 hub_search→hub_call이었다. 네이티브 ToolSearch
이벤트가 확인됐다고 표현하지 않는다. 설정 이름만으로 내부의 모델 로딩 과정을 단정하지 않았다.
기본 native 조건도 CLI가 제공하는 실제 동작이며, 인위적으로 모든 스키마를 eager-loading한
API 조건으로 부르지 않는다.

## 실제 사용량: 도구가 필요 없는 과제

각 2회 중앙값. 단일 세션에서 READY만 답하도록 했다.

| 조건 | input_tokens | cached_input_tokens | 차이값(input−cached) | 시간 |
|---|---:|---:|---:|---:|
| 기본 native 10 | 14,811 | 11,648 | 3,163 | 4.982초 |
| 기본 native 100 | 14,811 | 11,648 | 3,163 | 5.204초 |
| direct 생략 설정 100 | 14,811 | 5,824 | 8,987 | 4.868초 |
| Hub 검색 경로 100 | 14,810 | 5,824 | 8,986 | 5.132초 |

이 과제에서는 목록이 10개에서 100개로 늘어도 입력 토큰이 늘지 않았다. 이것만으로 모든
시점·모든 대화에서 도구 정의가 무료라는 결론은 내리지 않는다. 콜드 세션의 초기 응답과
클라이언트의 비동기 초기화·로딩 정책이 함께 반영된 관측이다.

## 실제 사용량: 도구 조회 과제

각 2회 중앙값. input과 cached는 CLI가 보고한 해당 turn의 누적 값이다. 단일 최초 프롬프트
크기가 아니며 검색·호출로 생긴 여러 모델 요청을 포함한다.

| 조건 | input_tokens | cached_input_tokens | 차이값(input−cached) | 시간 |
|---|---:|---:|---:|---:|
| 기본 native 10 | 49,787 | 43,008 | 6,779 | 12.215초 |
| 기본 native 100 | 73,741 | 65,152 | 8,589 | 16.706초 |
| direct 생략 설정 100 | 84,073 | 64,960 | 19,113 | 17.732초 |
| Hub 검색 경로 100 | 61,096 | 50,944 | 10,152 | 17.165초 |

실제 16회 모두 수용 조건을 통과했다. 검색 경로는 큰 native 목록보다 누적 입력은 적었지만
비캐시 입력이 더 많았고 시간도 일관된 우위를 보이지 않았다. 캐시 상태와 추가 호출 단계가
다르므로, 작은 시간 차이를 통계적으로 유의한 속도 차이로 해석하지 않는다.
`input−cached`는 비교를 위한 차이값이며 실제 청구 금액이나 구독 한도 소모량이 아니다.

최초 예비 실행에서 headless 승인 정책 때문에 hub_search가 거부된 사례가 있었다.
이는 모델이나 검색의 과제 실패율로 집계하지 않았다. 승인·준비 조건을 맞춘 최종 16회만
위 표에 사용했다. 별도의 예비 실행과 모형 결과를 섞지 않았다.

## 실제 Claude Code 요청 구조

Claude Code 2.1.233, 격리 HOME·MCP 설정, 로컬 모형 API와 가짜 키를 사용했다.
최소 모드는 ToolSearch 자체를 빼므로 제외하고 정상 tool set에서 비교했다.
MCP 도구 검색을 ENABLE_TOOL_SEARCH=true 또는 false로 명시했다.

| 조건 | 첫 요청에 실린 합성 catalog 함수 정의 | 선택 후 다음 요청 |
|---|---:|---:|
| 검색 켬, catalog 10개 | 0개 | 선택한 2개 |
| 검색 켬, catalog 100개 | 0개 | 선택한 2개 |
| 검색 끔, catalog 100개 | 100개 | 추가 단계 없음 |

검색 켬의 최초 요청에는 기본 도구와 DeferredToolPlaceholder가 있었고 catalog의 전체 함수
스키마는 없었다. 실제 ToolSearch 실행으로 선택된 두 이름의 정의와 참조만 다음 요청에 추가됐다.
따라서 MCP tools/list에 100개가 있어도 모델 요청에 매번 100개 전체를 넣는 것은 아니다.

이 단계의 모델 응답은 수동으로 조종한 모형이다. 실제 모델이 올바른 두 도구를 찾는 비율이나
실제 Claude 토큰·시간·비용으로 계산하지 않았다. Codex의 로컬 provider/전송 탐색 캡처도
실제 로그인된 모델 경로와 같다고 입증되지 않아 모델 로딩 결론에 사용하지 않았다.

## 추천을 어떻게 고치는가

- 공용에 등록할 만한 MCP를 **목록이 커진다는 이유만으로 제외하지 않는다**.
- 현재 클라이언트의 검색·지연 로딩 지원, 실제 usage, 프로세스 유지 비용을 따로 확인한다.
- native MCP가 적합한 작업을 CLI로 강제 전환하지 않는다. CLI+skill과 MCP를 작업별로 선택한다.
- Context7·MarkItDown은 문서 기능의 필요성으로 검토한다. 브라우저·게임·영상 스킬은 스택 적합성으로 고른다.
- 서버의 등록과 연결·실행을 구분한다. 검색을 지원해도 서버 프로세스의 메모리가 없어지는 것은 아니다.
- 모든 연결을 숨기는 검색 전용 Hub 정책은 보류한다. native 도구·Apps 호환성을 유지한다.
- 초기 조사에서의 기능 적합성·중복 검토는 유지하지만, 목록 JSON을 토큰 비용으로 해석한 추천은 철회한다.

## 한계와 재현 자료

이는 2종의 쉬운 합성 과제와 조건별 2회 반복이다. 실제 개발 과제의 정확도·보안·장기 대화의
누적 컨텍스트·다른 모델·클라이언트 버전을 대표하지 않는다. 한 번에 고정 수의 MCP를 연결하는
보편적인 최적값이나 특정 스킬의 품질 향상률을 산출한 실험도 아니다.

실험 코드·원자료·검증 집계는 로컬 `.local/integrations/client-loading/`에 보관했다.
`real-controlled/summary.json`은 최종 실제 실행, `validated-summary.json`은 검증한 집계,
`captures/`는 모형 요청 구조 자료다. 개인 런타임 메시지가 포함될 수 있어 공개 번들에 넣지 않는다.
