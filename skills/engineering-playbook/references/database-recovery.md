# DB 복제·승격·복구 (PLAYBOOK §25.5)

## 선택 기준

DB를 primary/replica로 구성하면 무엇을 얻으려는지 먼저 구분한다.
읽기 확장, 빠른 장애 전환, 재해 복구는 서로 다른 요구다.
§7의 DB 소유권 규칙은 복제본을 추가해도 유지한다.

| 방식 | 이점 | 반드시 수용할 비용 |
|---|---|---|
| 단일 DB + 백업 | 운영 단순, 비용 낮음 | 복원 동안 중단 |
| 비동기 replica | 읽기 분산, 승격 후보 | 복제 지연·미전달 쓰기 손실 가능 |
| 동기 복제 | 구성한 확인 수준의 내구성 강화 | 쓰기 지연, standby 장애 시 대기 가능 |
| 관리형 HA | 승격·운영 자동화 | 서비스별 보장·비용·종속성 |

❌ replica가 있으므로 백업과 복원 훈련은 생략한다.

✅ 삭제·오염도 복제되므로 독립 백업과 WAL/PITR 복원을 별도로 검증한다.

## 승격 계약

- 장애 판정과 승격 담당자를 하나로 정한다. 여러 자동화가 동시에 승격하지 않는다.
- 기존 primary를 쓰기 대상에서 격리하는 fencing을 설계한다.
- 애플리케이션의 쓰기 endpoint, 풀 폐기, 재연결, 재시도 범위를 명시한다.
- read-after-write가 필요한 API는 primary로 읽거나 충족 조건을 별도로 정의한다.
- replica lag, WAL 보관량, replication slot이 유발하는 디스크 증가를 감시한다.
- 과거 primary의 재합류는 재동기화 절차로 수행한다. 그대로 writable로 되돌리지 않는다.

## 복구를 완료했다고 말할 조건

복구 시작부터 서비스 정상화까지 RTO를 측정한다. 복원 데이터의 최신 시점과
사고 시점 차이를 RPO로 기록한다. 아래 항목을 증거와 함께 남긴다.

1. 백업·WAL 목록과 checksum, 암호화 키 접근 가능 여부.
2. 격리 환경 복원, 목표 시점까지 재생, 스키마·행 수·업무 불변식 확인.
3. 잘못된 삭제 이전 시점 복구와 정상 쓰기 재개.
4. DB뿐 아니라 파일 스토리지·설정·인증키도 함께 복구 가능한지 확인.
5. 실측 RPO/RTO, 누락 데이터와 수동 조치, 다음 훈련 일자.

백업은 독립 장애 영역·권한으로 보관한다. 세부 보안은 `security-ops.md` §12.
초기 프로젝트에서 HA 운영 여력이 부족하면 관리형 서비스를 먼저 비교한다.
