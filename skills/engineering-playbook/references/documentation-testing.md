# 문서 정합성·테스트 품질·작업 분할 (PLAYBOOK §26)

## 문서 구조 (§26.1)

문서의 읽는 순서는 `00-index.md`, `01-...md`로 표현한다. 각 주제에 독립적인 읽기
흐름이 생기면 하위 폴더와 `00-index.md`를 만든다. 문서 수만으로 폴더를 쪼개지 않는다.
요구사항에는 `REQ-...`, 결정에는 `ADR-...`, 작업에는 `WP-...`처럼 경로와 독립인 ID를 둔다.

- vision: 누구의 어떤 문제를 해결하는가, 성공 기준.
- scope: 이번에 제공할 것, 보류한 것, 검증된 한계.
- architecture: 경계, 상태 원천, 계약, 실패·보안 모델.
- ADR: 맥락, 선택, 대안, 결과, 대체된 결정.
- development: 독립 작업 단위, 테스트, 통합 순서.
- operations: 설치, 복구, 업데이트, 장애 대응.

## 정합성 검사 (§26.2)

| 검사 | 자동화 가능한 것 | 사람이 판단할 것 |
|---|---|---|
| 문서 연결 | 링크·참조 경로·중복 ID | 빠진 요구사항과 결정 |
| 계약 | JSON/OpenAPI·설정 키·CLI smoke test | 필드 의미와 오류 처리 |
| 용어 | glossary 기준 명칭·폐기 용어 검색 | 같은 단어의 다른 의미 |
| 상태 | 작업별 테스트·증거 경로 | 성공 기준이 목적을 충족하는가 |

요구사항 → 설계 → 코드 → 수용 테스트 → 운영 문서를 연결한다.
새 문서가 기존 ADR을 대체하면 양쪽 상태와 링크를 갱신한다.
AI 검토는 모순 후보를 제시하며 진실을 보증하지 않는다.

❌ API 경로를 바꾸고 코드 테스트만 통과했다고 완료한다.

✅ 계약·예제·CLI·UI·운영 문서의 경로를 함께 확인하고 재현 가능한 호출을 남긴다.

## 테스트를 통과시키는 테스트 피하기 (§26.3)

명세의 외부 관찰 결과로 기대값을 작성한다. 구현의 계산식을 테스트에 복사하거나,
검증해야 할 로직까지 mock하지 않는다. 실패·경계값·권한·불변식을 함께 검증한다.
테스트가 실패할 때 기대값 변경 전에 요구사항과 구현 중 무엇이 잘못됐는지 판단한다.

❌ `assert actual == implementation_helper(input)`로 같은 코드끼리 비교한다.

✅ 독립적인 기대값과 경계값을 사용하고, 잘못된 구현에서 실제로 실패하는지 확인한다.

뮤테이션 테스트는 분기 반전, 경계 연산자 변경, 반환값 변경, 호출 제거 등에 테스트가
실패하는지 확인한다. 핵심 도메인·인증·데이터 손실 관련 코드부터 적용한다.
Java는 PIT, 다른 언어는 해당 생태계 도구의 지원 버전·실행 비용을 확인한다.
점수만 목표로 하지 않는다. 살아남은 변이는 테스트 누락·동등 변이·요구사항 누락으로
분류하고 이유를 기록한다. 동등 변이 때문에 100%를 무조건 강제하지 않는다.

## 병렬 작업 계약 (§26.4)

각 작업은 목적, 소유 파일, 의존성, 입력·출력 계약, 실패 예시, 수용 테스트,
검증 명령, 완료 증거를 가진다. 소유 파일이 겹치거나 계약이 미정이면 먼저 분리한다.
mock만 통과한 작업은 통합 완료가 아니다. 실제 adapter를 연결한 통합 테스트를 별도로 둔다.
작업자 수보다 계약 확정이 우선이다. 사람·단일 에이전트·서브에이전트에 같은 작업서를 쓴다.
