# 시스템 아키텍처와 DB 소유권 (PLAYBOOK §3, §4, §7, §12)

## 시스템 구조의 최소 단위 (§3)

서비스를 설계할 때 항상 세 축을 명시한다:

- **논리**: 역방향 프록시, API, 워커, DB, 캐시, UI — 각각 **역할 한 줄**로 적을 수 있어야.
- **물리**: 컨테이너/프로세스 단위로 **무엇이 무엇에 의존**(DB 주소, Redis 유무)하는지 그림이나 표.
- **데이터**: **"원장의 단일 소스"가 어디인지**(DB? 이벤트 스트림?) 먼저 정한다. **캐시는 부가물**.

원칙은 "같은 호스트에서 라우팅이 섞이지 않게 제약을 건다" 정도로 일반화 — 구체 기술(Traefik, 라벨, 네트워크 격리)은 팀 스택에 맞춰.

## 아키텍처 판단 (§4)

요구가 들어오면 이 순서로 묻는다:

- **요청–응답 안에 끝나는가** → API/함수 레벨로 충분.
- **수 분 이상·재시도·부분 실패**가 있는가 → 워커·큐·스케줄러 후보.
- **캐시**: 미스 시 **항상 같은 원천**으로 수렴하는가. **TTL vs 무효화** 중 어느 쪽인가.
- **비밀·토큰**: 저장소에 넣지 않고 **환경 변수**, 예시는 `.env.example`만.
- **외부 API 부하**: 간격·동시성 상한·타임아웃을 **환경 변수**로 노출 → 운영에서 조절.

## DB 소유권 (§7) — 매우 중요

### 기본 (§7.1)

- **DB 스키마·ORM·마이그레이션은 API 서비스 한 곳에서만** 다룬다.
- 워커·배치·다른 프로세스는 **DB에 직접 붙지 않고**, API의 **REST(또는 합의된 내부 API·이벤트)** 로만 읽고 쓴다.
- 누가 물으면 답: **"DB는 API만 담당하고, 나머지는 API를 통해서만 붙인다."**

### 예외: `shared` ORM 패키지 (§7.2)

- API와 워커가 같은 패키지로 모델을 공유하는 모노레포 방식은 **기본 허용 목록에 없다.**
- **구두로 명시적으로 허용했을 때만** 쓴다 (담당자가 "이번 건은 shared로 가자"고 입으로 승인).
- 예외 프로젝트는 **README/이슈에 한 줄** "`shared` ORM 사용 — 구두 승인(일자·누구)" 남긴다.

### 미래 (§7.3)

- 조직·트래픽이 커지면 예외였던 저장소도 **§7.1 기본**으로 맞추는 것이 자연스럽다 (워커 → API만 호출).

## 최적화·운영 태도 (§12)

- 먼저 **측정 가능한 병목**(쿼리 한 번, N+1, 불필요한 직렬화) 제거 → 그 다음 동시성 늘리기.
- **외부 시스템**: "내 서버가 버틴다"보다 **상대가 망가지지 않게** — 스로틀·백오프·타임아웃을 기본값으로.
- 프록시 뒤에서는 **좁은 경로 규칙이 넓은 규칙보다 우선**(SPA 폴백과 API 경로 충돌 방지).

## 신규 작업 체크 (요약 — 자세한 건 `checklist.md`)

- I/O 바운드인가 CPU 바운드인가 (§2)
- 실패 시 사용자/운영자에게 무엇이 보이는가
- 설정이 환경 변수로 노출, 기본값이 안전한가
- 의존성 경계(공유 vs 앱 전용)가 깨지지 않았는가
- 워커가 DB에 직접 붙으면 §7.1 기본인지, §7.2 예외(구두 승인+기록)인지
- replica/워커 수를 늘릴 수 있는가 (§2.6). 수신과 처리가 붙어 있다면 버퍼·큐 경계는?
