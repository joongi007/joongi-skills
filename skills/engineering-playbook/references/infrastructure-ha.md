# 인프라 선택과 고가용성 (PLAYBOOK §25.1~§25.3)

## 먼저 정할 것 (§25.1)

프로젝트마다 허용 중단 시간, RPO(허용 데이터 손실), RTO(복구 목표 시간),
장애 영역(프로세스·노드·존), 운영 담당자를 기록한다. 개발 환경의 복제본 수를
운영 가용성의 근거로 사용하지 않는다. 숫자에는 측정일과 부하 조건을 붙인다.

| 상황 | 먼저 검토 | 도입 전에 확인 |
|---|---|---|
| 개인 로컬 도구 | 단일 프로세스 + 파일 백업 | 재시작·파일 손상 복구 |
| 작은 서비스 | 단일 DB + 자동 백업, 필요하면 관리형 DB | 복원 실측이 RTO 이내인가 |
| 짧은 중단도 손실이 큰 서비스 | 복제 + 자동 승격 + 클라이언트 전환 | 분할 상황에서 쓰기 주체가 하나인가 |
| 노드·존 장애를 견뎌야 하는 서비스 | 독립 장애 영역 분산 | 스토리지·DNS·LB도 함께 살아남는가 |

## Redis / Valkey 선택 (§25.2)

Redis 전체를 하나의 라이선스로 취급하지 않는다. 조사 시점 기준 Redis ≤7.2는
BSD-3-Clause, 7.4는 RSALv2/SSPLv1, ≥8.0은 RSALv2/SSPLv1/AGPLv3 선택이다.
실제 도입 버전의 LICENSE와 재배포·서비스 제공 조건을 확인한다.
Valkey는 BSD 계열 대안을 원할 때 후보이며 모듈, 명령, 클라이언트,
백업 포맷과 운영 도구의 호환성을 검증한다. 이름만 바꾸고 호환된다고 가정하지 않는다.

선택 ADR에는 버전, 라이선스, 필요한 기능, 대안, 이전·롤백 방법을 적는다.
새 캐시를 넣기 전에 유실 시 원천에서 복원 가능한지, 원장처럼 쓰고 있는지 확인한다.

## Sentinel의 실패까지 설계 (§25.3)

- Sentinel은 비클러스터 Valkey의 감시·승격·현재 primary 주소 조회를 제공한다.
- **장애 판정 quorum과 failover 승인 과반수는 다르다.** 설정 quorum만 살아 있어도
  전체 Sentinel의 과반수 승인을 얻지 못하면 승격되지 않을 수 있다.
- 보통 서로 다른 노드에 3개, 필요하면 5개를 둔다. 홀수는 장애 허용 대비 효율적이며
  짝수 자체가 프로토콜 위반은 아니다. 한 노드의 Sentinel 3개는 노드 장애에 함께 죽는다.
- 클라이언트에 복수 Sentinel 주소, 대상 서비스명, 인증·TLS와 재조회·재연결을 설정한다.
- `down-after-milliseconds`, `failover-timeout`, `parallel-syncs`는 네트워크 지연,
  데이터량, 복구 예산을 측정해 정한다. 작은 숫자가 항상 안전한 것은 아니다.
- 구성 파일 재기록과 재시작 후 상태 복구가 가능한 저장 위치를 제공한다.
- 비동기 복제에서 승인된 쓰기가 유실될 수 있다. 쓰기 제한 정책도 손실 범위와
  가용성의 교환이며 강한 일관성 보장을 대신하지 않는다.

❌ primary 주소를 환경 변수에 고정하고 Sentinel 프로세스만 추가한다.

✅ 클라이언트가 Sentinel을 통해 primary를 찾고, 전환 후 기존 풀 연결을 폐기한다.

### 수용 테스트

| 장애 주입 | 확인할 결과 |
|---|---|
| Sentinel 하나 중지 | 감시 지속, quorum·과반수 조건 충족 |
| primary 노드 전원 차단 | 승격 시간 + 클라이언트 재연결 시간 측정 |
| 과반수 Sentinel 격리 | 소수 파티션에서 무리한 승격을 하지 않음 |
| 재연결 중 쓰기 응답 유실 | 멱등성 정책대로 중복·불확실 결과 처리 |
| 전체 재시작 | 구성·데이터 복원, 원장과 정합성 확인 |
