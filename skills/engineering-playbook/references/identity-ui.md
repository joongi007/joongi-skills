# 인증 UI 커스터마이징 (PLAYBOOK §19, §20)

로그인 화면의 브랜드 통일과 인증 프로토콜 변경은 별개다. Keycloak 등 IdP의 공식
확장 지점을 먼저 사용하고, 디자인을 맞추려고 앱에서 사용자 비밀번호·OTP를 수집해 중계하지 않는다.
사용하는 디자인 시스템의 토큰·접근성 기준을 적용한다.

## 변경 범위 선택

| 필요한 변경 | 출발점 | 검토할 비용 |
|---|---|---|
| 로고·색상·글꼴·문구·언어 | 기존 테마 상속 + CSS·자산·메시지 번들 | 로그인·계정·관리·메일의 적용 범위 차이 |
| 레이아웃·상호작용 | 필요한 템플릿만 override | 부모 템플릿 변경·폼·스크립트 호환성 |
| 계정·관리 콘솔 전체 재구성 | 공식 console 확장 또는 별도 UI와 서버 측 관리 API | 광범위한 권한·회귀·업그레이드 비용 |

Quick Theme 같은 보조 도구는 배포 버전에서 지원 상태를 확인한다. 확인일 기준 공식 가이드는
실험/preview 기능으로 안내하므로 운영의 필수 경로로 무조건 채택하지 않는다.
커뮤니티 빌드 도구를 선택할 때도 Keycloak 버전·테마 종류·라이선스·의존성 지원을 확인한다.

## Keycloak 테마 적용 절차

1. 배포 버전·부모 테마·변경할 종류(login/account/admin/email 등)를 정한다.
   필요한 종류의 `theme.properties`에 부모·styles·messages를 설정하고 CSS·이미지·번역을 추가한다.
   부모 전체를 복사하기보다 작은 override를 유지한다. 로그인 테마가 모든 콘솔을 바꾸지는 않는다.
2. 기존 앱과 테마의 토큰·자산 원본을 정하고 복사본이 필요하면 재생성·차이 검사를 제공한다.
   다른 서비스의 자산을 그대로 가져오지 않고 라이선스·고지를 함께 관리한다.
3. 개발에서는 테마 캐시를 끄고 읽기 전용 테마 mount로 빠르게 확인할 수 있다.
   운영은 캐시를 켜고 검증한 테마를 버전 있는 이미지/artifact에 포함한다. 임의 서버 파일 수정을 배포 절차로 삼지 않는다.
4. 테마를 배포한 뒤 대상 realm의 Themes 설정에서 해당 종류를 선택한다.
   기존 realm은 표시 설정만 멱등적으로 갱신하고 이전 값을 보관한다. 전체 realm import·DB 초기화로
   테마를 적용하지 않는다. 테마 선택과 인증 flow·client·가입 정책 변경을 분리한다.
5. 업그레이드마다 부모 템플릿·CSS·인증 스크립트 차이를 검토하고 실제 인증 흐름을 재검증한다.
   서버 버전·테마 버전·설정의 호환 조합과 이전 테마로 되돌리는 절차를 남긴다.

## 보존할 보안·UX 계약

- 공식 폼의 전송 대상·hidden field·CSRF/세션 값·MFA·WebAuthn·required action을 보존한다.
  테마 변경으로 오류 메시지·재시도·세션 만료·취소·복구 경로가 사라지지 않게 한다.
- template escaping을 유지하고 사용자 입력을 HTML·JavaScript로 해석하지 않는다.
  로그인·계정 화면에 불필요한 분석·광고·외부 script/font/CDN을 넣지 않는다.
  CSP를 느슨하게 풀어 시각 효과를 구현하지 않는다. 테마 artifact도 신뢰한 출처에서 검토·빌드한다.
- 비밀번호·OTP·복구 코드·QR·쿠키·토큰이 로그·캡처·trace·분석 수집에 포함되지 않게 한다.
  테스트는 합성 계정으로 하고 민감 화면은 수집하지 않거나 필요한 부분을 가린다.
- 키보드 순서·label·focus·대비·작은 화면·긴 번역·언어 전환·오류 읽기를 확인한다.
  로그인 성공 화면만 캡처하지 말고 실패·비밀번호 표시·만료·MFA·로그아웃·복구도 기능 검사한다.
- 인증 공급자와 앱 사이 이동을 사용자가 알아볼 수 있게 한다. 제품명·버전 표시를 줄이는 것은
  공격 표면 제거·인증 보안 강화의 대체 수단이 아니다.
