# 보안 탐지·차단·복구 (PLAYBOOK §29)

예방으로 공격 표면을 줄이면서, 침해 가능성에 대비해 탐지·대응 시간을 줄인다.
완전 차단 불가능성을 예방을 생략할 이유로 쓰지 않는다. 아래는 프로젝트에 맞춰 구체화할 가이드이며
모든 환경에서 같은 알림 임계치·자동 차단·시간 목표를 강제하는 표준은 아니다.

## 설계할 때 정할 것

| 항목 | 정할 내용 |
|---|---|
| 보호 대상 | 사용자 계정·키·데이터·배포 권한·백업, 유출·변경·중단의 영향 |
| 위협 시나리오 | 토큰 탈취, 권한 확대, 진단 endpoint 노출, 비정상 반출, 의존성 변조 등 |
| 관측 | 무엇을 어디에서 기록하며 어떻게 연관시킬지, 수집 중단도 어떻게 감지할지 |
| 초기 조치 | 제한·세션 폐기·키 폐기·연결 비활성·격리 중 가능한 최소 범위 |
| 책임 | 알림 수신자·대체 연락처·판단 담당자·해제 및 서비스 복구 담당자 |
| 검증 | 가짜 비밀로 재현하는 검사와 복구·오탐 해제 훈련 |

## 관측과 신호

- 시간·상관관계 ID·행위자 식별자·대상·결과·거절 이유·조치·rule 버전을 구조화해 기록한다.
  식별자에는 필요한 경우 가명·제한된 보관 기간을 적용한다. 원문 비밀을 증거로 남기지 않는다.
- 비밀번호·토큰·쿠키·Authorization·DB 연결 문자열·키·개인정보 본문을 기본 로그에서 제외한다.
  외부 문자열의 개행·길이를 제한해 log injection과 저장소 고갈을 막는다.
- 인증 실패만 보지 말고 성공한 이상 행위도 본다. 권한 변경, 관리 endpoint 접근,
  세션 재사용, 데이터 읽기량·전송량 증가, 새 외부 목적지, 비정상 프로세스 실행을 조합한다.
- 고정 임계치와 평소 패턴·업무 시간·배포 이벤트를 함께 고려한다. CPU 증가 하나만으로 침해로 확정하지 않는다.
- 수집 지연·queue/drop·디스크·알림 전송 실패를 따로 경보한다. 로그가 조용한 것과 안전한 것은 다르다.
- 중요 로그는 다른 권한 경계로 전송하고 변조·삭제를 감시한다. 호스트가 침해되면 로컬 로그만 신뢰하지 않는다.

## 신뢰도와 조치 범위

| 신호 예시 | 초기 대응 | 자동화 조건 |
|---|---|---|
| 일시적인 인증 실패·단일 부하 상승 | 관측·상관 분석·해당 경로 rate limit | 사용자 전체를 잠그는 수단으로 악용되지 않게 함 |
| 탈취가 확인된 세션·토큰 | 해당 세션/토큰 폐기·재인증·관련 사용 이력 확인 | 정확한 대상 식별, 전파 지연·재시도·실패 검사 |
| 의도하지 않은 dump endpoint 공개 | 해당 관리 경로 차단·접근 범위 조사 | 운영 probe까지 차단하지 않는 제한된 rule |
| 확인된 악성 실행·키 노출 | 관련 workload·자격증명 격리, 담당자 호출 | 사전 승인된 playbook·제한된 대응 계정·복구 수단 |

자동 대응에는 대상·기간·최대 영향 범위·멱등성·조치 감사 로그·해제 조건을 둔다.
처음에는 관측 모드로 오탐을 확인하고 좁은 범위부터 적용한다. 신뢰도가 낮은 신호만으로
전체 네트워크·계정·DB를 막거나 증거를 지우는 자동 조치는 기본으로 두지 않는다.
차단 성공 응답만 보지 말고 기존 세션·캐시·다른 replica에도 제한이 반영됐는지 확인한다.

## 사고 시 실행 순서

1. 영향 범위·현재 진행 여부를 분류하고 담당자를 호출한다. 사고 ID와 시간선을 만든다.
2. 진행 중 피해를 줄이도록 최소 범위로 제한·격리한다. 가능한 증거를 함께 보존하되,
   증거 수집을 끝낼 때까지 계속되는 반출을 방치하지 않는다.
3. 공격에 쓰인 세션·키·권한을 폐기하고 재발급한다. 유출 키는 파일 삭제만으로 복구되지 않는다.
4. 진입점·설정·공급망을 고친 뒤 신뢰할 수 있는 이미지·백업으로 복구한다. 특권 침해라면
   침해 호스트에서 도구·로그·키 교체 결과를 그대로 신뢰하지 않는다.
5. 권한·데이터 무결성·서비스 동작·추가 반출 여부를 확인하고 단계적으로 제한을 해제한다.
6. 영향 대상 통지·신고·증거 보관 의무는 관할·계약·사고 유형에 맞춰 담당자가 확인한다.
7. 탐지 rule·차단 범위·복구 절차·회귀 검사를 갱신한다. 원인과 놓친 신호를 함께 기록한다.

## 속도를 측정하는 방법

각 사고·훈련에 `첫 관측 가능한 신호 → 탐지 → 담당자 확인 → 제한 적용 → 검증된 복구` 시간을 남긴다.
실제 침해 시작 시점을 모르면 추정치로 구분한다. 평균뿐 아니라 p95·미탐 시나리오·알림 유실·오탐·
차단으로 생긴 서비스 피해를 본다. MTTD/MTTR 이름만 쓰지 말고 시작·종료 시점과 분모를 정의한다.

시간 목표는 예를 들어 '확인된 토큰 탈취를 수분 내 해당 토큰 폐기'처럼 서비스 위험·운영 인력·
검증 가능한 신호에 맞춰 정한다. 이 수치는 NIST의 공통 의무나 보장 시간이 아니다.
모의 침해·알림 경로 단절·중복 알림·키 폐기 실패·복구 실패·오탐 해제를 정기적으로 훈련한다.

## 프로젝트 규모별 시작점

개인 프로젝트는 구조화 로그·간단한 알림·수동 폐기/중지 절차·복구 가능한 백업부터 시작한다.
운영 범위가 커지면 중앙 수집·상관 분석·온콜·제한된 자동 대응을 추가한다.
SIEM·EDR·Falco·클라우드 탐지 제품은 관측 공백과 운영 가능성을 보고 선택하며 전부 필수로 설치하지 않는다.
이 가이드는 Hub에 자동 침해 탐지·격리 엔진을 추가했다는 뜻이 아니다.
