# 외부 통신 경계와 캐시 정책 (PLAYBOOK §4, §12, §27)

외부 HTTP·SDK 통신은 대상 시스템별 adapter/client로 모으고 업무 유스케이스는 명시한 port에 의존한다.
공통 transport에는 연결 풀·timeout·TLS 검증·제한된 재시도·관측을 두되, 모든 외부 서비스를
하나의 거대한 client로 합치지 않는다. 인증과 원격 DTO 변환은 해당 adapter가 책임진다.
사용자 입력 URL은 SSRF 검증을 거치고 토큰·본문 원문을 로그나 캐시 키에 넣지 않는다.

캐시는 같은 port를 구현한 decorator로 둘 수 있다. 예: `PricePort`를 구현한
`CachedPriceAdapter`가 `HttpPriceAdapter`를 감싼다. 이것은 구현 선택지이며 모든 호출에 캐시를 강제하지 않는다.

## 조회 모드를 계약으로 구분하기

| 모드 예시 | 흐름 | 사용 조건·실패 처리 |
|---|---|---|
| `cached` (cache-aside) | 유효한 캐시 hit → 반환; miss → 원천 조회 → 캐시 저장 | 오래된 값 허용 범위·TTL을 정한 반복 읽기 |
| `refresh` (캐시 읽기 우회 + 갱신) | 원천 조회 → 더 최신인 경우 캐시 교체 → 원천 결과 반환 | 사용자가 새로고침하거나 최신 원천 확인이 필요할 때 |
| `bypass` (읽기·쓰기 모두 우회) | 원천 조회 → 그대로 반환 | 저장 금지 데이터·진단 등. refresh와 혼동하지 않기 |

`refresh`는 원천 읽기 뒤 캐시를 채우는 정책이다. 원천의 **쓰기**와 캐시 쓰기를 결합하는
write-through와는 다르다. 모드 이름은 프로젝트 계약에 맞추되 의미를 API·테스트·문서에서 일치시킨다.
새로고침도 외부 호출 비용을 발생시키므로 권한·호출량 상한을 적용한다.

## 정합성과 장애의 경계

- 원천이 기준이다. TTL만으로 정합성을 보장하지 않는다. key에는 tenant·권한 범위·조회 인자·스키마 버전을
  반영하고 권한 검사보다 캐시를 먼저 반환하지 않는다. 민감 데이터는 저장 필요성·암호화·보관 기간을 검토한다.
- 원천 쓰기 성공 후 해당 key를 무효화하거나 버전으로 갱신한다. DB와 cache의 원자성이 없으면
  실패 재처리·이벤트/outbox·유효 기간으로 복구할 수 있게 한다. 캐시 실패가 이미 성공한 원천 쓰기를 되돌렸다고 표시하지 않는다.
- 느린 옛 조회가 새 refresh·무효화 뒤 도착해 최신 값을 덮어쓸 수 있다. 원천 revision·조건부 교체·generation 검사로
  경합을 막는다. 요청 시작 시각만으로 원천 데이터의 최신성을 판정하지 않는다. 불확실하면 오래된 결과를 캐시에 저장하지 않는다.
- 같은 key의 miss 폭주는 single-flight·동시성 제한·TTL jitter로 줄인다. 프로세스 내부 single-flight가
  다른 API 복제본까지 보호한다고 가정하지 않는다. 원천으로 우회하는 호출량에도 상한이 있어야 한다.
- 원천 성공·캐시 저장 실패 때 원천 결과를 반환할지 정하고 실패를 관측한다. 원천 실패 시 stale 허용은
  업무별 명시적 정책으로 둔다. `refresh` 실패를 오래된 값으로 조용히 성공 처리하지 않는다.
  권한·결제 판단처럼 오래된 결과가 위험한 경로에서는 stale fallback을 사용하지 않는다.
- 캐시 장애·timeout, miss 폭주, tenant 간 격리, 쓰기와 늦은 조회의 경합, refresh 갱신 실패를 검사한다.
  hit 비율만 보지 말고 원천 호출량·지연·stale 비율·갱신 실패도 측정한다.
