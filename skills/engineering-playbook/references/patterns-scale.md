# 규모에 맞는 패턴과 실제 예시 (PLAYBOOK §27)

패턴 이름보다 해결하려는 변화·실패를 먼저 적는다. 문서에는 문제, 선택 이유,
최소 예제, 도입 조건, 비용, 실패 사례, 검증 방법을 함께 둔다.

| 상황 | 적용 패턴과 실제 예시 | 도입 조건 | 주요 비용·실패 |
|---|---|---|---|
| 외부 MCP 버전 차이 | Adapter: 2025 initialize를 내부 계약으로 변환 | 서로 다른 wire 계약 공존 | 상태·취소 의미를 손실시키는 변환 |
| 도구가 너무 많음 | Registry + lazy discovery: 설명 검색 후 schema 조회 | 전체 schema의 컨텍스트 비용이 큼 | 검색 누락·오래된 인덱스 |
| 외부 장애 전파 | Bulkhead: upstream별 제한된 동시성·시간 예산 | 느린 서버가 다른 요청에 영향 | 상한을 너무 높게 잡아 격리 실패 |
| 반복 실패 호출 | Circuit breaker: 연속 실패 후 제한적 탐침 | 호출 비용·장애 전파가 관찰됨 | 과민한 차단·영구 차단 |
| 분 단위 계산 | Task/state machine: 실행 ID로 상태·결과 조회 | 단일 요청 예산 초과 | 재시작·취소·중복 실행 미정 |
| DB와 이벤트 동시 기록 | Transactional outbox: 같은 트랜잭션에 이벤트 기록 | DB commit과 publish 유실 방지 필요 | relay·중복 소비·정리 운영 |
| 캐시 조회 가속 | Cache-aside: miss 시 원천 조회 후 TTL 저장 | 측정된 반복 읽기 병목 | stampede·stale 데이터 |

❌ 작은 로컬 도구에 사용하지 않는 Redis·큐·Kubernetes를 먼저 설치한다.

✅ 상태·부하·복구 요구를 측정하고 가장 작은 구성으로 충족한다. 확장 경계는 보존한다.

## 규모는 사용자 수 하나로 결정하지 않기

| 단계 | 판단 자료 | 기본 출발점 |
|---|---|---|
| 개인·로컬 | 동시 요청, 디스크 상태, 복구 가능성 | 단일 프로세스, 파일·SQLite, 명확한 모듈 |
| 작은 팀·제품 | p95 지연, DB 부하, 배포 빈도, 운영 인원 | 모듈형 단일 서비스, 관리형 DB 후보 |
| 여러 인스턴스 | 세션 공유, 멱등성, 풀 상한, 장애 영역 | 상태 외부화, 제한된 수평 확장 |
| 독립 팀·큰 시스템 | 독립 배포·소유권, SLO, 데이터 경계 | 필요 경계만 서비스로 분리 |

서비스 분리는 코드 줄 수보다 소유권·배포·장애 격리 필요로 판단한다.
작은 시스템이어도 금전·데이터 손실 요구가 엄격하면 HA가 먼저 필요할 수 있다.
큰 시스템이어도 모든 모듈을 별도 서비스로 나눌 이유는 없다.

## 코드 그래프 도구 적용

코드 그래프는 함수 호출·참조·의존 관계를 분석한 데이터다. MCP는 이를 조회하는
인터페이스 중 하나다. GitNexus 같은 그래프 도구나 Serena 같은 심볼 탐색 도구를
연결할 때 언어 지원, 프로젝트 경계, 분석 시점·커밋, dirty 상태와 재색인 비용을 확인한다.
동적 호출·생성 코드·런타임 구성은 그래프에서 빠질 수 있으므로 테스트를 대체하지 않는다.
처음에는 읽기 전용 영향 분석에 사용하고 편집 도구는 별도 권한으로 다룬다.
