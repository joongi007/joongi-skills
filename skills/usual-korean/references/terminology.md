# 용어 선택과 용례 조사

## 선택 순서

1. **정확한 원문이 필요한가?** 제품명, API 필드, 명령어, 실제 UI 라벨이면 원래 표기를 유지한다.
2. **프로젝트에서 정한 용어가 있는가?** 기존 문서·용어집과 맞춘다. 부정확한 용어라면 의미 차이를 먼저 설명한다.
3. **독자가 평소 쓰는 말인가?** 영어·음역·번역어 중 가장 익숙하면서 정확한 표현을 고른다.
4. **낯선 개념인가?** 필요한 경우 첫 등장에만 짧은 설명이나 원어를 덧붙인다.

원어가 더 정확하다고 항상 영어를 고집하지 않는다. “저장”을 “세이브”로,
“설정”을 “컨피규레이션”으로 바꿀 이유는 없다. 반대로 “버튼”을 “단추”로,
“팔로우”를 “따라가기”로 바꾸는 것이 언제나 더 자연스러운 것도 아니다.

| 상황 | 권장 표현 | 판단 기준 |
|---|---|---|
| SNS 기능 설명 | SNS에 팔로우 버튼이 있어요. | 익숙한 약어와 외래어 |
| 영문 화면 조작 안내 | 프로필에서 `Follow`를 누르세요. | 실제 라벨과 일치 |
| 한국어 화면 조작 안내 | 프로필에서 **팔로우**를 누르세요. | 실제 한국어 라벨과 일치 |
| 개발자용 장애 문서 | Redis 연결 타임아웃을 3초로 설정합니다. | 제품명·익숙한 기술 용어·단위 보존 |
| 일반 사용자용 오류 | 서버에 연결하지 못했어요. 잠시 후 다시 시도해 주세요. | 내부 구현보다 사용자의 행동 안내 |
| 새 개념 도입 | failover(장애 발생 시 다른 서버로 전환) | 독자에게 필요한 첫 설명만 제공 |

위 예시는 문맥별 선택 예시다. 모든 프로젝트에 적용하는 고정 용어집은 아니다.

## 검색이 필요한 경우

용어 뜻이 불확실하거나, 후보 표현이 서로 다른 기술 개념을 가리키거나,
새 제품·기능의 한국어 표기가 불분명하면 웹에서 확인한다.
흔히 쓰는 “버튼”, “로그”, “캐시”까지 매번 검색하지 않는다.

- 먼저 대상 제품의 공식 한국어 문서나 실제 UI를 확인한다. 기술 의미는 공식 원문과 대조한다.
- 공식 번역이 없거나 독자에게 낯설면 국내 기술 문서·업계 발표 등 독자가 접하는 용례도 비교한다.
  언어 규범을 확인하는 일과 현업에서 쓰는 표현을 확인하는 일을 구분한다.
- 검색어에 제품·분야·후보를 함께 넣는다. 예: `Kubernetes 공식 문서 한국어 readiness probe`.
  검색 결과 제목이나 출현 횟수만 보고 표준 용어라고 단정하지 않는다.
- 공식 자료 하나로 명확하면 그 근거로 결정한다. 번역이 충돌하면 추가 자료를 비교하고,
  그래도 애매하면 원어와 짧은 설명을 쓴다. 취향 때문에 검색을 계속하지 않는다.
- 조사한 선택을 설명할 때 실제 확인한 페이지 링크를 붙인다. 중요한 프로젝트 용어는
  용어집에 선택한 표현·원어·적용 범위·출처·확인 날짜를 기록한다.
- 웹을 쓸 수 없으면 조사한 것처럼 말하지 않는다. 기존 용어 또는 원어를 유지하고,
  의미에 영향을 주는 불확실성만 밝힌다.

한 문서에서 같은 개념의 표기를 일관되게 유지하되, 코드의 `timeout`과 설명의 “타임아웃”처럼
역할이 다른 표기까지 억지로 하나로 통일하지 않는다.
