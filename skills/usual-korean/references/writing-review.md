# 문장 작성과 검토

## 문맥별 기준

- 대화에서는 핵심 답을 먼저 말하고 필요한 이유를 덧붙인다. 사용자의 말투를 과장해서 따라 하지 않는다.
- 기술 문서는 어떤 조건에서 누가 무엇을 하는지 밝힌다. “그것”, “해당 처리”가 무엇인지 모호하면 이름을 쓴다.
- UI에서는 화면의 실제 동작에 맞춰 쓴다. 실행하지 않은 저장·완료를 성공한 것처럼 표현하지 않는다.
- 윤문은 원문의 목적과 어조를 유지한다. 격식을 줄여 달라는 요청이 없다면 존댓말을 반말로 바꾸지 않는다.
- 자연스러움은 문맥으로 판단한다. 피동문·목록·전문 용어가 유용하면 그대로 쓴다.

## 적용 예제

| 입력·상황 | 수정 예 | 확인할 점 |
|---|---|---|
| 소셜 네트워크 서비스에 따라가기 기능이 있는 단추가 있어요. | SNS에 팔로우 버튼이 있어요. | 사용자가 말한 기능과 자연스러운 용어 |
| 연결 실패 시 재시도 수행 가능. | 연결에 실패하면 다시 시도할 수 있습니다. | 조건과 가능성 보존 |
| 배포 완료. 서비스 정상 동작 미확인. | 배포는 완료했지만, 서비스가 정상적으로 동작하는지는 아직 확인하지 못했습니다. | 완료한 작업과 미확인 상태를 구분 |
| 캐시 활용을 통해 조회 성능 개선을 수행합니다. | 캐시를 사용해 조회 성능을 개선합니다. | 내용 없이 길어진 동사 줄이기 |
| 요청은 3초 후 실패할 수 있습니다. | 요청은 3초 후 실패할 수 있습니다. | 이미 명확한 문장은 유지 |
| 장애가 나도 데이터 유실은 없습니다. | 원문을 유지하고 사실 확인이 필요하다고 별도로 알립니다. | 문체 교정으로 잘못된 보장을 정당화하지 않기 |
| “항상 성공한다”라는 직접 인용 | 인용문은 그대로 둡니다. | 인용자의 주장과 작성자의 판단 구분 |

문장을 줄이면서 “일부”를 “모두”로, “가능하다”를 “보장한다”로,
“최대 3초”를 “3초”로 바꾸면 의미가 달라진다. 자연스러워 보여도 되돌린다.

## 결과를 내기 전

원문과 수정본의 사실·수치·단위·조건·부정·불확실성을 비교한다.
독자가 동작을 이해하는 데 필요한 정보가 남아 있는지, 실제 제품 라벨과 기술 용어가 정확한지 확인한다.
긴 문서를 나눠 고쳤다면 용어와 문체가 문단 사이에서도 이어지는지 확인한다.

이 예제들은 사람이 검토할 적용 사례다. 특정 문자열이 나왔다는 이유만으로
문체의 품질을 자동 판정하거나 AI 작성 여부를 단정하지 않는다.
