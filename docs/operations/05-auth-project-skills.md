# 인증·프로젝트 범위·스킬 관리

문서 ID: OPS-AUTH-PROJECTS · 요구사항: REQ-REGISTRY, REQ-SKILL, REQ-INSTALL

## 연결한 MCP에 로그인하기

Hub는 단일 사용자 loopback 서비스다. Hub 자체에 Keycloak이나 사용자 로그인을 추가하지 않았다.
관리 API는 기존 Host·Origin 검사와 세션 토큰을 사용한다. 이 토큰과 upstream 서비스의 토큰은 별개다.
로컬 프로세스와 OS 계정을 신뢰하는 모델이며, 다른 사용자에게 원격 공개하는 서버가 아니다.

### 에이전트에서 시작하기: stdio·HTTP 공통

에이전트에게 “Notion 로그인을 시작해줘”라고 요청한다. Hub는 다음 도구를 제공한다.

| 도구 | 역할 |
|---|---|
| `hub_auth_start({"server":"notion"})` | 로그인 링크를 생성한다. 에이전트가 사용자에게 링크를 보여준다. |
| `hub_auth_poll({"server":"notion","login_id":"반환된 ID"})` | 사용자 승인 후 상태를 확인한다. device code 방식은 반환된 interval을 따른다. |
| `hub_connect({"server":"notion"})` | 인증 완료 후 연결·도구 목록을 갱신한다. |

사용자가 링크를 브라우저에서 열고 계정·workspace·접근 권한을 직접 승인한다.
비밀번호나 토큰을 채팅에 붙여넣지 않는다. access token·refresh token·PKCE verifier·Hub 관리 세션은
도구 결과에 포함하지 않는다. 에이전트가 알아야 할 정보는 로그인 링크와 상태뿐이다.
Notion의 흐름은 [공식 OAuth·PKCE 안내](https://developers.notion.com/guides/mcp/build-mcp-client)를 따른다.

순수 stdio에서도 관리 웹 서버를 미리 실행할 필요가 없다. 로그인 중에만 callback 전용
loopback 포트를 열고, 완료·10분 만료·MCP 연결 종료 시 닫는다. 이 포트에는 관리 API나
웹 화면이 없다. 같은 에이전트 세션을 유지한 채 승인하고, 세션을 종료했다면 새 로그인 링크를 만든다.
공용·프로젝트 로그인의 callback과 인증 저장 범위를 섞지 않는다. API key·Basic 등 수동 비밀 입력 방식은
기존 관리 화면 또는 환경변수 설정을 사용한다.

처음 연결이 인증 오류로 실패하면 응답에도 `hub_auth_start`와 대상 서버 ID를 안내한다.
도구가 보이지 않는 구버전 세션은 MCP 연결을 다시 열거나 새 에이전트 세션을 시작한다.

### 관리 화면에서 시작하기

MCP 연결 → 해당 서버의 **인증**을 펼쳐 방식을 저장한 뒤 로그인한다.
인증 방식을 바꾸면 **인증 설정 저장**을 먼저 누른다. 저장 전에는 로그인·비밀 값 저장을 막고,
선택한 인증 방식에 해당하는 입력과 행동만 보여준다.
OAuth는 **로그인 시작 → 브라우저에서 계속**을 누르고 서비스에서 동의한 뒤 Hub로 돌아와
**연결 확인**을 누른다. 동의·서비스 계정 가입·MFA를 에이전트가 대신 승인하지 않는다.

| 방식 | 설정·행동 |
|---|---|
| none | 인증 없는 서버 |
| bearer | token_env로 환경변수 이름 지정 또는 로컬 비밀 값 저장 |
| api_key | token_env, header, 선택적 prefix. 기존 headers 환경변수 매핑도 지원 |
| basic | username_env·password_env 또는 로컬 사용자 이름·비밀번호 저장 |
| oauth | 브라우저 Authorization Code + PKCE S256, state·issuer·resource 검사 |
| device_code | 서비스가 지원하면 코드 입력 후 로그인 완료 확인. poll 간격 준수 |
| client_credentials | client_id·client_secret_env 필수. 사용자 동의 없는 서비스 계정 grant |
| external | stdio 서버 자체 CLI 로그인·자격증명 저장소·env 매핑 사용 |

원격 MCP 주소는 HTTPS를 사용한다. HTTP는 실제 연결할 IP가 모두 loopback일 때만 허용한다.

HTTP OAuth는 WWW-Authenticate의 Protected Resource Metadata, RFC 8414와 OIDC discovery,
사전 등록 client ID, 서버가 지원하는 CIMD 또는 Dynamic Client Registration을 처리한다.
client secret은 환경변수로 주고 client_secret_basic 또는 client_secret_post를 지정할 수 있다.
토큰 갱신·refresh token rotation, 401 이후 한 번의 갱신·재시도, 선택적 provider revocation을 지원한다.
권한 확대는 자동 동의하지 않는다. 서버가 요청한 scope를 확인하고 다시 로그인한다.

고급 설정에는 `issuer`, `resource_metadata_url`, `client_auth_method`, `client_metadata_url`,
개별 `*_endpoint`를 넣는다. CIMD는 실제 HTTPS client metadata 문서와 현재 callback 등록이
필요하다. 로컬 Hub가 외부에서 접근 가능한 CIMD 문서를 자동 발행하지는 않는다.
브라우저 OAuth 서버는 metadata에 S256 지원을 명시해야 한다. 고정 callback 포트가 필요한
제공자는 Hub의 포트를 고정하고 UI에서 사용하는 `http://127.0.0.1:포트/oauth/callback`을 등록한다.

```json
{"type":"oauth","client_id":"registered-id","issuer":"https://identity.example.com","scopes":["read"],"client_secret_env":"EXAMPLE_CLIENT_SECRET","client_auth_method":"client_secret_basic"}
```

인증 URL은 HTTPS 또는 loopback HTTP만 허용하고, metadata·token 요청의 redirect는 따르지 않는다.
토큰과 비밀번호는 서버 등록 JSON·도구 결과·화면 상태·요청 로그에 내보내지 않는다.
인증 저장은 OS 보안 저장소를 사용하며 평문 fallback은 없다. 환경변수 값은 파일로 복사하지 않는다.

| 환경 | 저장 방식·준비 |
|---|---|
| Windows | 로그인한 Windows 사용자의 DPAPI로 credentials.json 암호화 |
| WSL | Windows PowerShell을 통해 같은 사용자의 DPAPI 사용, 비밀은 stdin으로 전달 |
| macOS | 로그인 Keychain의 generic password, 로컬 파일에는 항목 식별자만 저장 |
| Linux | Secret Service·로그인 키링과 `secret-tool`·`gdbus` 필요, 파일에는 식별자만 저장 |

매 호출마다 비밀번호나 승인을 요구하는 방식은 아니다. 로그인 키링이 열린 상태에서 사용한다.
잠긴 키링·headless Linux에서 저장소가 없으면 오류를 내며 OS에서 잠금을 해제하거나 저장소를 설정한 뒤
다시 시도한다. macOS의 Keychain 접근 정책에 따라 최초 접근을 사용자가 별도로 허용해야 할 수 있다.
Hub가 자동 팝업을 반복해서 띄우거나 평문 파일로 우회하지 않는다.

```bash
joongi-hub credentials
# 이전 버전의 평문 인증이 있다면 사용 중인 각 범위의 state-dir에서 명시적으로 이전
joongi-hub credentials --migrate
```

복사한 파일은 다른 OS 계정에서 복호화되지 않을 수 있다. Keychain·Secret Service 항목은 원래
상태 경로와 묶이므로 state 경로 이동 후에는 재로그인이 필요하다. 이전 평문 백업은 새 저장소를
확인한 뒤 별도로 정리한다. 키링 보호도 실행 중인 Hub 자체의 악성 동작을 막지는 않는다.
인증 해제는 로컬 저장 값을 지우고 가능한 경우 서비스 토큰을 철회한다. 환경변수·서버 CLI의
로그인 상태나 서비스의 모든 세션을 삭제하지는 않는다.

private_key_jwt, mTLS, DPoP, SAML 직접 로그인, 토큰 교환·회사별 비표준 SSO는 전용 구현이 필요하다.
모든 제공자의 실제 계정으로 검증한 것은 아니다. Device Code·Client Credentials도 서비스가
해당 grant를 지원해야 한다. stdio는 HTTP OAuth를 강제로 적용하지 않고 해당 서버의 인증 방식을 쓴다.

## 프로젝트마다 사용할 것만 선택하기

**프로젝트 범위 → 프로젝트 등록**에서 현재 컴퓨터의 절대 경로와 가져올 공용 스킬·MCP를 선택한다.
기본은 공용 항목을 가져오지 않는다. 상단 작업 범위를 바꾸면 선택한 카탈로그·연결·Tasks·인증을 사용한다.
공용 서버를 가져와도 인증 토큰은 프로젝트마다 따로 저장한다. 공용 서버 설정 변경은 상속에 반영되고,
같은 ID의 프로젝트 연결을 저장하면 그 프로젝트 설정이 우선한다. 상속 연결 자체를 제외하려면
프로젝트의 공용 MCP 선택을 해제한다.

프로젝트 스킬은 `.agents/skills`, `.claude/skills`, `.cursor/skills`, `.github/skills`,
`.gemini/skills`, `.opencode/skills` 순서로 찾는다. 같은 이름이면 먼저 발견한 프로젝트 스킬이
공용 스킬보다 우선한다. `skill_paths`로 이 목록을 줄이거나 순서를 바꿀 수 있다. 등록되지 않은
스킬은 URI를 직접 입력해도 읽을 수 없다. 프로젝트 밖 경로와 symlink는 허용하지 않는다.
프로젝트 등록을 해제해도 소스 파일이나 설치된 스킬을 삭제하지 않는다.

추가 회사·개인 출처는 source ID가 붙은 이름으로 [카탈로그 설정](14-catalog-preferences.md)에서 등록한다.
개별 스킬·서버·출처 또는 개발·문서·디자인·도구 묶음을 현재 범위에서 제외할 수 있다.
이 선택은 Hub의 읽기·검색·native 목록 경로에 적용하며 에이전트가 직접 읽는 사본은 자동 삭제하지 않는다.
native 사본은 설치 계획 또는 `--exclude-category` 선택으로 별도로 관리한다.

에이전트에는 프로젝트 카드의 **에이전트 연결 설정**을 등록한다. 핵심 인자는 다음과 같다.

```bash
python3 -m joongi_hub stdio --state-dir /path/to/hub-state --profile project-id
```

기본은 지정한 범위의 독립 stdio다. 혼합 모드는 같은 state의 실행 중인 HTTP Hub를 공유한다.
세 가지 연결 방식과 웹에서의 에이전트 등록은 [연결 설정](06-connection-modes.md)을 본다.
한 연결의 profile을 다른 profile로 바꾸는 요청은 거절한다. 이는 Hub 내 작업 분리이며,
악의적인 로컬 사용자에 대한 접근 제어·샌드박스는 아니다.
에이전트가 자체적으로 읽는 전역 스킬이나 별도로 등록한 MCP까지 숨기지는 않는다.
완전한 분리가 필요하면 해당 에이전트의 전역 설정도 확인하고 프로젝트 전용 연결을 사용한다.
다른 프로젝트나 기존 에이전트 설정을 자동으로 삭제하지 않는다.

## 스킬 설치·업데이트·제거

스킬 라이브러리의 **설치 관리**에서 작업·스킬·에이전트를 고르고 **변경 계획 보기**를 누른다.
대상 경로와 보호할 파일을 확인한 다음 **이 계획 적용**을 누른다. MCP에서도
`hub_skills_status`, `hub_skills_plan`, `hub_skills_apply`로 같은 기능을 사용한다.
`hub_auth_status`는 비밀 값 없이 현재 범위의 인증 상태를 반환한다. OAuth 로그인은 위의 에이전트 시작 흐름도 지원하며, 수동 비밀 입력은 로컬 UI에서 한다.

공용 범위는 사용자 스킬 폴더에, 프로젝트 범위는 프로젝트 스킬 폴더에 복사한다.
Claude·Codex·Cursor·Copilot·Gemini·OpenCode 중 대상을 고를 수 있다. 이 관리 기능은 스킬만
변경하며 에이전트 실행 파일이나 MCP 설정은 수정하지 않는다. 기존 설치 스크립트의 소유권 manifest를
재사용한다. 새 에이전트에도 **설치** 계획을 만들거나 기존 설치 명령을 다시 실행한다.

작업·스킬·에이전트·배포 출처 갱신 선택을 바꾸면 기존 계획을 무효화한다.
요청 중 선택을 바꾼 경우 늦게 도착한 계획도 표시하지 않는다.
계획은 15분간 유효하고 원본 스냅샷·대상 파일·manifest가 바뀌면 재계획해야 한다.
다른 도구가 설치했거나 직접 수정한 파일을 덮어쓰지 않는다. 적용 실패 시 installer가 복구한다.
프로젝트 복사본은 기본 버전 고정이며, 업데이트하려면 **고정 해제**를 먼저 적용한다.
`joongi-skills.lock.json`은 버전·digest·고정을 기록하고, 기기별 관리 정보는 `.joongi/private/`에 둔다.
프로젝트의 자체 스킬을 공용으로 복사하거나 설치 출처의 스킬을 자동 수정하지 않는다.

업데이트의 **등록된 배포 출처 갱신**은 설치 때 기록한 다운로드 주소가 있을 때 사용한다.
클론 출처는 사용자가 `git pull --ff-only`로 갱신한 뒤 적용한다. 임의 URL이나 프로젝트 소스가
MCP 인자만으로 공용 배포 출처가 되지 않는다. 에이전트의 스킬 재탐지는 새 세션이 필요할 수 있다.

검증은 [검증 기록](../development/03-verification.md)을 본다.
공식 근거: [MCP 2025 인증](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization),
[MCP 2026 인증 보안](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations).

## 웹 화면의 새로고침과 읽기

같은 범위에서 새로고침하거나 메뉴를 옮겨도 작성 중인 인증·MCP·프로젝트 폼과 스킬 관리
선택을 유지한다. 비밀 값도 현재 탭의 DOM 메모리에만 남으며 localStorage·sessionStorage에
저장하지 않는다. 범위를 바꾸거나 탭을 닫으면 편집 값은 비운다. 프로젝트 전환 실패 시
오류 화면에서 **다시 연결**로 복구하며, 이전 범위의 목록을 현재 범위처럼 표시하지 않는다.

스킬 문서는 기본 Markdown 읽기 보기로 표시하고 **원문 보기**로 전환할 수 있다.
제목·표·목록·코드·HTTP(S) 링크와 스킬 내부 참조를 지원한다. HTML은 텍스트로 보여주고
실행하지 않는다. 전체 CommonMark·중첩 목록·이미지 렌더러를 제공한다는 의미는 아니다.

## 도구 실행 승인

로컬 stdio에서 인증이 필요한 도구를 호출하면 사용자 확인을 요청한다.
2025-11-25 form elicitation을 협상한 호스트에서는 앱 안의 입력 폼으로 이번 호출을 선택한다.
그 밖의 환경은 브라우저 승인함을 사용한다. [호스트별 조건](12-3d-and-host-consent.md#gui-앱-안에서-호출-선택). 같은 사용자·프로젝트 상태 경로의 요청은 stdio 프로세스가 달라도 승인함 하나에
모이며 MCP별로 구분한다. 새 요청은 목록에 자동으로 추가하고 별도 창을 열지 않는다.
관리 웹을 미리 켤 필요는 없다. Windows·WSL에서는 Windows 기본 브라우저를,
macOS·Linux에서는 OS의 기본 브라우저 연결을 사용한다. 에이전트가 실행되는 컴퓨터에 창이 열린다.
브라우저를 사용할 수 없는 SSH·headless 환경에서는 자동으로 승인하지 않으며,
로컬 소유자가 `joongi-hub open`으로 기존 관리 화면을 열어 처리할 수 있다.

1. 승인함에서 MCP별 요청을 고르고 프로젝트 범위·연결 주소·도구·인수를 확인한다.
   여러 요청을 처리하려면 체크한 뒤 **선택 N개 이번 호출 허용** 또는 **선택 N개 거절**을 누른다.
   **현재 목록 모두 선택**은 그 시점의 요청만 선택한다. 이후 도착한 요청은 자동 선택·승인하지 않는다.
   일괄 처리는 이번 호출 범위만 지원하고, 일부 요청이 만료·처리됐다면 전체 변경 없이 거절한다.
2. 허용 범위에서 **이번 호출만**, **이 도구 1시간 허용**, **이 도구 항상 허용** 중 고른 뒤 승인한다.
   1시간·항상 허용은 현재 프로젝트 범위와 MCP 연결의 같은 도구에 다른 인수·페이지를 넣는 호출도 포함한다.
   **거절**이나 창 닫기는 허용을 만들지 않는다.
3. 에이전트는 `hub_approval_status({"approval_id":"응답의 요청 ID","wait_seconds":20})`로 확인한다.
   이 조회는 사용자 결정을 최대 20초 기다렸다가 반환한다. 생략하면 즉시 현재 상태를 반환한다.
   `approved`이면 원래 도구와 인수·후속 요청을 그대로 재시도한다. 승인창이 직접 실행하지 않는다.

에이전트는 `hub_approval_request({"approval_id":"응답의 요청 ID"})`로 기존 대기의 승인창을
요청할 수도 있다. 같은 대기를 재요청해도 열린 창을 중복 생성하지 않는다.
`pending`은 사용자 대기, `denied`는 거절, `unavailable`은 만료·소비·다른 범위의 요청을 뜻한다.
거절한 동일 요청은 기존 5분 유효 시간이 끝날 때까지 다시 승인 요청을 만들지 않는다.
에이전트는 거절을 받은 호출을 자동 반복하지 않아야 한다.

승인 권한이 담긴 주소는 OS 브라우저에만 전달하며 MCP 결과에는 포함하지 않는다.
에이전트에는 요청 ID·상태·브라우저 열기 성공 여부만 전달한다. 승인창은 별도 임시 loopback
포트에서 동작하며, 프래그먼트의 비밀을 주소에서 바로 지우고 메모리에만 둔다.
판정 POST는 비밀·Host·Origin을 검증하고 GET 요청·다른 요청 ID·재사용을 차단한다.
비밀 없이 화면을 여는 것만으로는 인수 조회나 승인이 되지 않는다. 외부 스크립트와 관리 API도 없다.
승인·거절 후에는 응답 유실 확인을 위한 읽기 전용 결과를 최대 30초 보관한다.
승인함 창의 수명은 이 결과 보관과 별도로 관리한다.
결과 확인 세션에서는 재승인·거절 변경·인수 조회를 허용하지 않으며 최대 32개로 제한한다.
공유 승인함의 lease는 인증된 화면 연결로 갱신한다. 명시적인 창 닫기·owner stdio 종료 때 해제하고,
종료 신호가 누락되면 최대 120초 뒤 다른 stdio가 새 승인함을 열 수 있다. 절대 수명은 8시간이다.
열린 승인함은 같은 범위의 새 요청을 처리할 수 있지만 다른 프로젝트 저장소에는 접근하지 못한다.

버튼을 누르면 즉시 **승인 저장 중**과 경과 시간이 표시되고, 저장을 확인한 뒤 **승인 완료**로 바뀐다.
승인 완료는 서비스 호출의 완료를 뜻하지 않는다. 에이전트가 원래 요청을 재시도해야 하며
Notion 등의 실행 결과는 에이전트에서 확인한다. 브라우저 요청은 5초로 제한하고, 응답을 못 받으면
3초 제한의 읽기 전용 상태 조회로 저장 여부를 확인한다. 자동으로 승인 POST를 반복하지 않는다.
확인에도 실패하면 **승인 상태 다시 확인**으로 복구할 수 있으며 성공한 것처럼 표시하지 않는다.

승인함의 **대기 요청이 없으면 30초 후 자동 닫기**는 기본 선택된다. 승인 저장을 확인하고
대기 목록이 비어 있는 동안만 유예 시간을 센다. 새 요청이 오면 닫기를 취소하고 기존 창에 추가한다.
닫기 직전에도 서버가 대기 요청이 없는지 원자적으로 확인한다. **이 창 유지**나 체크 해제로 자동 닫기를 끌 수 있다. 거절·오류·확인 불가 상태에서는
자동으로 닫지 않는다. 브라우저가 외부에서 열린 탭의 자동 닫기를 제한하면 수동 탭 닫기 안내를 남긴다.
설정 화면은 저장할 때 자동으로 닫지 않는다.

이 방식은 MCP 클라이언트의 네이티브 승인 대화상자를 요구하지 않는다.
기존 MCP 연결 화면의 **호출 승인**도 계속 사용할 수 있다. 로컬 stdio가 HTTP로 중계하는
관리형 HTTP·hybrid 모드에서도 브라우저는 로컬 중계 프로세스가 연다. HTTP bearer만 가진
직접 연결은 로컬 소유자 권한이 없으므로 브라우저를 열지 못하며 관리 화면에서 승인한다.
MCP 인수나 `_meta`로 이 제한을 바꿀 수 없다.

일반 MCP 도구 호출이 사용자 승인에서 멈추면 RPC 오류나 `isError`가 아닌 정상 도구 결과로
`structuredContent.status=approval_required`, `execution=not_started`와 다음 확인 도구를 반환한다.
실제 upstream은 아직 실행되지 않았다. 에이전트는 같은 호출을 반복하거나 실패로 보고하지 않고
승인 상태를 기다린다. 독립적인 다른 호출은 승인함에 계속 모을 수 있다.
Tasks로 실행한 호출은 `input_required`와 승인 대기 메타데이터를 유지하고, 승인되면 원래 호출을
재개한다. 거절·만료·취소는 실행 없이 작업을 취소한다. 정책 차단·실제 전송 오류는 계속 오류다.

출력 스키마가 있는 네이티브 도구는 원래 결과와 이 승인 대기 결과를 `anyOf`로 광고한다.
내부 참조는 원래 스키마 자원에 묶어 유지한다. 실제 upstream 출력의 필수 구조는 완화하지 않으며,
원격 서버가 Hub의 승인 대기 메타데이터를 흉내 내면 그 예약 필드를 제거한다.

이번 호출 승인의 기본 유효 시간은 5분이며 동시 호출도 한 번만 소비한다. 서버 설정·도구 정의·인수·MRTR 후속 입력과
동일한 호출만 실행할 수 있다. 반복 허용은 인수가 달라도 적용되며 1시간 뒤 만료되거나 사용자가 취소할 때까지 유지된다.
다른 프로젝트와 섞지 않으며, **MCP 연결 → 도구 호출 승인 → 반복 허용 내역**에서 취소한다.
취소하면 남아 있던 같은 허용의 승인 대기도 함께 무효화한다.

반복 허용은 연결 설정·확인된 도구 정의·매핑한 환경변수 값의 digest에 묶인다. 다음 호출에서
변경이 확인되면 허용과 연결된 승인 대기를 지우고 다시 확인한다. 로그아웃·새 로그인·수동 자격증명
교체도 허용을 취소하지만 정상적인 OAuth token refresh는 기존 허용을 유지한다.
인증 변경 식별자를 승인에 묶고 전송 직전에도 검사하므로, 승인 후 로그인이 바뀌면 새 계정의 자격증명으로 보내지 않는다.
서버가 같은 정의로 실제 동작만 바꾸는 경우까지 감지하는 보장은 아니다. `readOnlyHint`만으로 허용하지 않는다.
기존 수동 `allowed_tools` 설정은 별도의 명시적 허용 목록이며, 변경 감지를 하는 이 반복 허용과 구분한다.
쓰기 도구가 읽기 도구라고 선언해도 자동 승인하지 않는다. MRTR의 업무용 승인 입력은 이 보안 승인과 별개다.
자주 쓰는 신뢰한 도구는 **연결 설정**의 허용 목록에 실제 upstream 도구 이름으로 등록한다.
차단 목록이 우선하며 `*`는 전체 도구를 뜻한다. 인증 없는 서버에도 정책을 저장해 승인을 요구할 수 있다.
승인 대기에는 호출 인수가 포함되므로 상태 디렉터리를 공개하지 않는다.

## stdio 환경변수 전달

Hub의 전체 환경변수를 자식 MCP에 복사하지 않는다. PATH·홈·임시 경로·Windows 실행 변수·locale 등
실행에 필요한 기본 목록을 넘기며, 추가 값은 서버의 `env`에서 환경변수 이름으로 지정한다.
기존에 암묵적으로 전달되던 API key·SSH agent socket·proxy·추가 인증서·PYTHONPATH 등이 필요하다면
해당 서버에 필요한 것만 명시한다. 아래 예제는 실제 토큰 값을 등록 파일에 넣지 않는다.

```json
{"env":{"SERVICE_API_KEY":"MY_SERVICE_API_KEY","HTTPS_PROXY":"MY_COMPANY_PROXY"}}
```

환경변수 허용 목록은 우발적인 비밀 노출을 줄이는 조치이며, 그 자체가 파일 접근 샌드박스는 아니다.
외부 stdio MCP에는 별도의 [OS 실행 격리](10-security-boundaries.md)를 적용한다.
명시적으로 공유한 파일·변수의 악용이나 Hub 본체의 변조까지 막는다고 해석하지 않는다.
